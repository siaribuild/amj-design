# ops2 Attention — interaction spec

Stage 3 (UX). Inputs: `01-spec.md` (27 acceptance criteria), `02-design.md`
(module boundaries and the href table). Mock: `docs/mocks/ops2-attention.html`
— **the approved mock is the contract**; where this document and the mock ever
disagree, the mock is right and this document is the defect.

This document exists so the developer never has to make a design judgement
call. Every label, every message, every state, and every reuse decision is
below.

---

## 1. What the screen is

The console's gate. It answers one question — *which area needs a person, and
how much is waiting behind that door* — and then gets out of the way.

Three consequences, all of them binding:

- **A row leads, it never acts** (G1, G3). No approve, assign, dismiss,
  snooze, or mark-read control appears anywhere on this surface, at any width,
  in any state.
- **Zero is absence, not a number** (G2). A count of nought draws no row; a
  group whose counts are all nought draws no heading either. There is no
  dimmed row and no grey "0".
- **"Nothing is waiting" is only ever said after a successful count** (G4, G8).
  If the counts could not be read, the screen says so and draws no counts at
  all — not even ones that might be right.

## 2. Structure

### 2.1 The page frame

`OpsPage` (`src/ops2/chrome/OpsPage.tsx`), used exactly as the other
destinations use it, with no new props:

```tsx
<OpsPage destination="attention" title="Attention">
  …
</OpsPage>
```

- `title="Attention"` produces the desk toolbar `<h1.ops2-topbar__title
  .ds-type-heading-md>` and the phone band `<h1.ops2-page__title
  .ds-type-heading-lg>`. That `<h1>` is what the console's focus manager lands
  on (criterion 2) — nothing else on the page may be an `<h1>`.
- No `controls`, no `headActions`, no `headOverlay`, no `identity`. Attention
  has no toolbar of its own: it carries no search, no filter, no sort, and no
  refresh button. (Retry lives inside the error panel only.)
- `width` stays at its `"measure"` default. Six counts spread across a 27-inch
  monitor is a wall to scan; one column is a list to read. The desk frame in
  the mock shows the body at that measure deliberately — do not widen it.
- On the phone there is no top bar (the console's existing rule); the white
  band carries the name and the tab bar carries the destinations.

### 2.2 The body

```
.ops2-page__body                       (OpsPage owns this)
  └ .att-groups                        (new: the vertical rhythm between groups)
      └ <section> per drawn group
          ├ .att-group__head           (new: icon + <h2>)
          └ <ul.ops2-rows.att-rows.ds-surface-card>   (RowList)
              └ <li.ops2-row> per drawn count          (Row)
```

Group order is fixed and does not depend on the data: **Projects → Enquiries →
Customers**. A group appearing or disappearing therefore never moves the groups
above it (criterion 4, and assumption 1 of the spec).

Within Projects, the counts read in lifecycle order: new submissions → being
priced → ready to issue → awaiting payment.

### 2.3 The row

Each row is `Row` from `src/ops2/chrome/RowList.tsx`, with:

- `edge={null}` — **no leading edge on any Attention row.** That mark is
  reserved for the "critically wrong" kind of item, which is out of scope
  (spec §3, G1c). Attention rows are all the same kind of thing.
- `selected` unset — nothing on this screen is selectable.
- `onActivate` navigating to the row's href (below). Nothing else.

Row content:

```tsx
<span className="att-row">
  <span className="att-row__count">{count}</span>
  <span className="att-row__noun">{noun}</span>
</span>
<IonIcon className="ops2-row__chev" icon={chevronForwardOutline} aria-hidden="true" />
```

The chevron is the console's existing navigating-row mark
(`.ops2-row__chev`) — it is present because every Attention row navigates.

## 3. Copy — every string on the screen

### 3.1 Page and group headings

| Element | Copy |
|---|---|
| Page `<h1>` | `Attention` |
| Group heading (Projects) | `Projects` |
| Group heading (Enquiries) | `Enquiries` |
| Group heading (Customers) | `Customers` |

Group headings are `<h2>`. They match the destination names in
`nav/destinations.ts` exactly — the heading and the door say the same word.

### 3.2 Row copy

Sentence-style, the work not the field, **number leading** (spec assumption 6).
The count is rendered separately from the noun so it can be tabular and
leading, but the accessible name is the two read together.

| Count | Count slot | Noun slot | Reads as |
|---|---|---|---|
| `submissions` | n | `new submission` / `new submissions` | "4 new submissions" |
| `inReview` | n | `being priced` | "2 being priced" |
| `readyToIssue` | n | `ready to issue` | "1 ready to issue" |
| `awaitingPayment` | n | `awaiting payment` | "3 awaiting payment" |
| `newEnquiries` | n | `waiting for a reply` | "2 waiting for a reply" |
| `tradeApplications` | n | `trade application waiting on a decision` / `trade applications waiting on a decision` | "1 trade application waiting on a decision" |

Only two nouns pluralise (`new submission(s)`, `trade application(s)`); the
other four are already number-agnostic phrases and must not be pluralised.
Since a row is only drawn for a count of one or more, the singular form is only
ever needed at exactly 1 — a plain `n === 1 ? singular : plural` is the whole
rule.

Numbers render as-is, no thousands separator, no "99+" cap. `font-variant-numeric:
tabular-nums` on `.att-row__count` keeps 1 and 148 starting at the same place.

### 3.3 Empty panel (`.pq-empty`)

```
Nothing is waiting.
Every queue is clear. New submissions, unanswered enquiries and trade
applications appear here as they arrive.
```

Headline in `<strong>`, caption in `IonNote.ds-type-caption`. No illustration,
no icon, no button.

### 3.4 Counts-unavailable panel (`.pq-error`, `role="alert"`)

Shown for **both** a failed request and `degraded: true` — indistinguishable to
the reader by design (criteria 18, 19).

```
Can't tell you what's waiting.
The counts didn't load, so none are shown. This is not an empty console —
try again, or open Projects directly.
[ Try again ]
```

Button label: `Try again` (matches the queue's existing wording).

### 3.5 Unauthorised panel (`.pq-error`, `role="alert"`, **no button**)

Criterion 26. Same panel, different words, and no retry — pressing again fails
the same way.

```
This account can't see what's waiting.
The console is for staff accounts. Ask an administrator if you should have
access.
```

### 3.6 The Enquiries placeholder root

Uses the console's existing placeholder treatment verbatim (criterion 13).

```
Enquiries
Incoming enquiries that are not yet projects.
This destination isn't built yet.
```

Blurb in `.ops2-page__blurb.ds-type-body-md`, the second line in
`.ops2-page__pending.ds-type-caption` — same as `/customers`, `/pricing`,
`/files` and `/audit` today. The blurb string is the one `02-design.md` already
specifies for the destination registry; it is not duplicated in the page.

## 4. States

Exactly one of these five renders at a time. They are mutually exclusive: the
error panel never sits above a partial list, and the skeleton never sits above
rows.

| State | Condition | What renders |
|---|---|---|
| **Loading** | request in flight, no prior answer | `.pq-skeleton` (§4.1) |
| **Populated** | counts parsed, at least one > 0 | the groups (§2.2) |
| **Empty** | counts parsed, all six === 0 | `.pq-empty` (§3.3) |
| **Counts unavailable** | request failed, or `degraded` | `.pq-error` + Try again (§3.4) |
| **Unauthorised** | 401 / 403 | `.pq-error`, no button (§3.5) |

### 4.1 Loading

The shared `.pq-skeleton` container with a fixed shape — a heading bar, a
134px block, a heading bar, a 45px block. Loading cannot know how many rows are
coming, so the shape is a constant, chosen to sit close to the common case
(a four-row Projects group plus one more group). Criterion 21 asks the loading
shape to match what arrives; matching *approximately and stably* is the
achievable reading, and it is what the mock shows. Never a spinner.

`aria-busy="true"` on the skeleton container; the `<h1>` is present throughout,
so the focus manager has its target on first paint.

### 4.2 Refresh, and returning to the screen

`useSummary` copies `useProjectQueue`'s mechanics (design §2): one GET, a
stale-response guard, re-fetch on `ionViewWillEnter` (criterion 22).

**Re-entering the screen does not flash the skeleton.** If counts are already
in hand, the previous answer stays on screen while the new request runs, and
swaps when it lands. The skeleton is for the first load only — a screen that
blanks every time you tab back to it reads as broken.

If a re-fetch fails while previous counts are on screen, the error panel
replaces them. Stale counts are never left up: that is G4, and it is the whole
point of the screen.

### 4.3 Long content

- Row nouns wrap to a second line rather than truncating — a count nobody can
  read is worse than two lines. `.att-row` is `align-items: baseline` so the
  number stays aligned with the first line of a wrapped noun.
- Counts are unbounded (`148` renders as `148`). `min-width: 1.5ch` on the
  count keeps single digits from crowding the noun.
- Six rows is the maximum this screen can ever draw. There is no scroll
  strategy to design, no "show more", and no virtualisation.

## 5. Navigation — what a press does

| Row | Destination |
|---|---|
| new submissions | `/projects?wait=us` |
| being priced | `/projects?wait=us` |
| ready to issue | `/projects?wait=us` |
| awaiting payment | `/projects?wait=customer` |
| waiting for a reply | `/enquiries` |
| trade application(s) waiting on a decision | `/customers` |

All four Projects rows carry the wait axis alone (G7 option (i), criterion 12) —
so the count and the list that opens cannot disagree by construction.

### 5.1 The landing behaviour on Projects

The reader lands on the queue with the named wait chip **lit exactly as if they
had pressed it themselves** (criterion 10):

- `?wait=us` → `Needs us` chip active.
- `?wait=customer` → `Customer` chip active.
- Pressing `All` clears the filter and shows the whole queue. Pressing another
  chip switches to it. Neither is a special case — after landing, the queue
  behaves as it always does.
- The query parameter is a **one-shot instruction**: ProjectsPage consumes it
  in an effect and then `history.replace`s it away. So changing chips and
  pressing Back never re-applies a stale filter, and the URL never lies about
  what is on screen.
- The queue's own `Needs us` default is untouched when arriving any other way
  (criterion 9).

### 5.2 The two placeholder landings

`/enquiries` and `/customers` are placeholder roots today. That is correct and
intended (criteria 13, 14): the count is real work waiting, so G2 says draw the
row, and the door leads to the area that owns it. Nothing about the placeholder
needs new design — it is the treatment four destinations already have.

### 5.3 The rail and the tab bar

`enquiries` joins the `workspace` section after Customers (design §3). The
phone tab bar is **unchanged**: three destinations plus More (criterion 16) —
Enquiries reaches the phone through the More drawer, not the bar.

## 6. Component reuse map

Everything below already exists. The new CSS is one small file.

| Need | Existing thing | New props / classes |
|---|---|---|
| Page frame, `<h1>`, band, toolbar | `chrome/OpsPage.tsx` | none — `destination` + `title` only |
| List container | `chrome/RowList.tsx` → `RowList` | `className="att-rows ds-surface-card"` |
| Row | `chrome/RowList.tsx` → `Row` | `edge={null}`, `onActivate` |
| Row hover / press / focus | `styles/rows.css` | none — **no new state is added to the row** |
| Navigating-row chevron | `.ops2-row__chev` | none |
| Empty panel | `styles/projects.css` → `.pq-empty` | none |
| Error panel | `styles/projects.css` → `.pq-error` | none |
| Loading | `styles/projects.css` → `.pq-skeleton` + `IonSkeletonText` | none |
| Retry button | `IonButton size="small" fill="outline"` | none — same as the queue's |
| Warning icon | `warningOutline` from `ionicons/icons` | none |
| Placeholder destination root | `.ops2-page__blurb` / `.ops2-page__pending` | none |

### 6.1 The only new CSS — `src/ops2/styles/attention.css`

```css
.att-groups      { display:flex; flex-direction:column; gap:var(--theme-spacing-xl); }
.att-group__head { display:flex; align-items:center; gap:var(--theme-spacing-sm);
                   margin:0 0 var(--theme-spacing-sm); }
.att-group__head ion-icon { flex:none; font-size:1.125rem; color:var(--ds-text-muted); }
.att-group__head h2 { margin:0; font-family:var(--theme-font-display);
                      font-size:var(--theme-font-size-md);
                      font-weight:var(--theme-font-weight-semibold);
                      color:var(--ds-text-primary); }
.att-row         { display:flex; align-items:baseline; gap:var(--theme-spacing-sm);
                   flex:1 1 auto; min-width:0; }
.att-row__count  { flex:none; min-width:1.5ch; font-size:var(--theme-font-size-md);
                   font-weight:var(--theme-font-weight-semibold);
                   font-variant-numeric:tabular-nums; }
.att-row__noun   { min-width:0; font-size:var(--theme-font-size-base);
                   line-height:var(--theme-line-height-normal); }
.att-rows .ops2-row__open { padding-block:var(--theme-spacing-md); }
```

Every value is a token. No colour, radius or spacing step is invented; the
group icon reuses the destination's own `DESTINATION_ICON` entry.

The single line of row override (`padding-block`) exists because Attention's
rows carry one line of text where the queue's carry three — the shared 44px
minimum would leave them cramped against the hairline. It changes spacing only,
never a state or a colour.

## 7. Accessibility

- One `<h1>` (`Attention`), three `<h2>`s (the group names), and up to six
  links. That is the entire document outline.
- Each row's accessible name is the count and noun read together — "4 new
  submissions" — which is exactly what a sighted reader sees. Do not add
  `aria-label` overrides; the visible text is the label.
- The chevron and the group icons are `aria-hidden="true"`. They carry no
  information that the text does not.
- Focus ring: the console's existing inset `:focus-visible` ring on
  `.ops2-row__open`. Nothing new (mock §6).
- The error panels are `role="alert"`, matching the queue.
- `aria-busy="true"` on the skeleton container while loading.
- Touch target: rows are ≥44px by `.ops2-row__open`'s own minimum, and the
  `padding-block` override raises them, never lowers them.

## 8. A note for the architect and developer — the model's shape

`02-design.md` §2 gives each attention row a `label` string. The mock renders
the number in its own slot so it can be tabular and leading, which needs the
number and the noun separately.

**Recommended:** the model exposes `count`, `noun` and `href`, and derives
`label` as `` `${count} ${noun}` ``. The node suite's "the label starts with
its number" assertion then holds by construction rather than by inspection, and
the page renders `count` and `noun` into their two spans. This is a smaller
change than it looks — one extra field on a type that is already being written
— and it is the only deviation from the design this stage proposes.

## 9. Deliberately not designed

Recorded so the next reader knows these were considered and declined, not
missed:

- **A "checked just now" timestamp** on the empty state. It would make the
  empty state more trustworthy, but the screen already refuses to *show* an
  empty state it has not earned (§4), which is the real fix. Add it only if the
  owner reports distrusting a clear board.
- **The group heading as a link** to its destination. The rows below it already
  lead there, and a heading that is sometimes a link and sometimes not is a
  worse rule than a heading that never is.
- **Any leading edge / severity colour on rows.** Reserved for the
  "critically wrong" kind, which has no source yet (spec §3).
- **A manual refresh control.** `ionViewWillEnter` already re-fetches, and the
  error state carries its own retry.
- **Counts in the rail or the tab bar.** Not asked for, and it would put the
  same number in two places with two refresh lifecycles.
